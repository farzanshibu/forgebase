# Migrations

`system/` holds ForgeBase's own schema migrations for SQLite, `postgres/` the
same schema for PostgreSQL (ADR-0028 §7.6). Both are embedded in the binary at
build time by `crates/forgebase-migrations` and applied at startup
(`forgebase serve`, `forgebase init`) or explicitly (`forgebase migrate`).

Rules:

1. File name `NNNN_snake_case_name.sql`; `NNNN` is the version, strictly increasing.
2. Register every SQLite file in `SYSTEM_MIGRATIONS` (`crates/forgebase-migrations/src/lib.rs`)
   and every PostgreSQL file in `POSTGRES_MIGRATIONS`
   (`crates/forgebase-migrations/src/postgres.rs`); a test fails if a file is not registered.
3. **Never edit a migration that has shipped.** Its SHA-256 checksum is stored in
   `_forgebase_migrations`; a changed file makes the server refuse to start.
   Fix forward with a new migration.
4. Each SQLite migration runs inside one `BEGIN IMMEDIATE` transaction together with its
   bookkeeping row, followed by `PRAGMA foreign_key_check`. Statements that cannot
   run in a transaction (`VACUUM`, `PRAGMA journal_mode`, ...) are not allowed.
5. Migrations are forward-only. Rollback = restore the automatic snapshot that
   is written to `<data_dir>/backups/` before pending migrations are applied to an
   existing database (SQLite; PostgreSQL has no automatic snapshot yet: take a backup).

## PostgreSQL

6. `postgres/0025_baseline.sql` is the schema SQLite has after `system/0001` … `0025`,
   written once for PostgreSQL. Applying it records versions 1–25 with the SQLite names
   and the baseline's checksum, so a version means the same schema on both backends.
7. **From 0026 on every migration is a pair** with the same number and name:
   `system/NNNN_x.sql` and `postgres/NNNN_x.sql`. A PostgreSQL-only change gets a SQLite
   twin holding only a comment, and the reverse. The pairing test
   (`every_sqlite_migration_has_a_postgres_twin`) names the missing file.
8. A PostgreSQL migration runs in one transaction with `search_path = forgebase, public`
   (and `SET LOCAL ROLE forgebase_owner` where that role exists), so unqualified
   `_forgebase_*` names land in schema `forgebase`. Do not write `BEGIN`/`COMMIT`.
   Function bodies run with the caller's `search_path`: name the schema in them
   (`forgebase._forgebase_x`).
9. Use the type mapping of ADR-0028 §7.4: `INTEGER` → `bigint`, `INTEGER PRIMARY KEY` →
   `bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, booleans → `smallint CHECK (x IN (0, 1))`,
   `REAL` → `double precision`, JSON text → `jsonb`, `COLLATE NOCASE` → `citext`, `BLOB` → `bytea`;
   every foreign key `DEFERRABLE INITIALLY IMMEDIATE`; `RAISE(ABORT, msg)` triggers →
   `EXECUTE FUNCTION forgebase._forgebase_abort('msg')` (SQLSTATE P0001, same message).
10. `crates/forgebase-migrations/tests/schema_parity.rs` migrates both backends to the head
    and fails on any difference in tables, columns, types, nullability, defaults, keys,
    foreign keys, indexes, check counts, triggers or seed rows. Run it with
    `FORGEBASE_PG_ENGINE_DIR` set (it skips the PostgreSQL part otherwise).
