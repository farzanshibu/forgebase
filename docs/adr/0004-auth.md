# ADR-0004: Authentication core

- Status: accepted
- Date: 2026-11-07
- Work package: FB-20 (MDF-20)
- Scope: identities, credentials, token model, sessions and devices, key
  management, secret storage, abuse protection, CSRF, audit, and how a request
  becomes the data core's `AccessContext`.
- Builds on: ADR-0001 (crate direction, error envelope, data directory),
  ADR-0002 (dependency policy), ADR-0003 §7 (`AccessContext`, `Authorizer`,
  `SecretHasher`).
- Out of scope (later cards, extension points below): authorization rules and
  tenants (FB-21), OAuth/OIDC and WebAuthn (FB-22), SMTP/phone providers.

## 1. Crate and wiring

New crate `forgebase-auth` (depends on `forgebase-data`, `forgebase-core`,
`axum`; talks to the database only through `Arc<dyn Backend>`, never `sqlx`).

```text
forgebase-cli ──► forgebase-server ──► forgebase-api ──► forgebase-auth ──► forgebase-data ──► …
```

- `AuthService::open_with_data` builds the one `DataService` of the process
  with the Argon2id `PasswordHasher` as its `SecretHasher`, so `password`
  fields written through the data API (FB-11) are hashed too, and the auth
  service shares its catalog.
- `forgebase-server` opens it at startup and passes it to
  `AppState::from_data(..).with_auth(auth)`; `axum::serve` gets
  `ConnectInfo<SocketAddr>` so the client IP is known.
- `forgebase-api::router` merges `forgebase_auth::http::router()` (`/api/auth/*`)
  and installs `forgebase_auth::http::authenticate` directly **outside**
  FB-11's `install_anonymous` and **inside** request ids, CORS, tracing and the
  timeout. So handlers find the caller's `AccessContext` (or the anonymous one),
  and auth errors carry the normal envelope, request id and security headers.

Middleware order, outermost first: request context → CORS → trace → metrics →
panic catcher → timeout → **auth** → install_anonymous → hide_collection_existence → handler.

## 2. Identities

| Identity | Stored in | `AccessContext` principal |
|---|---|---|
| End user | a record of an **auth collection** (default `users`, created at server start if missing; ADR-0003 §3 fields `email`, `password`, `verified`, `token_key`) | `User { collection, id }` |
| Administrator (superuser) | `_forgebase_admins` (not a collection: no user rule can ever match it) | `Admin { id }` |
| Service account (machine) | `_forgebase_service_accounts`, role `service` or `admin` | role `admin` → `Admin { id: "sa:<id>" }`; role `service` → `User { collection: "_service_accounts", id }` |

`Subject` (in `forgebase-auth`) is the richer, `#[non_exhaustive]` identity;
the request also carries `Authenticated { subject, credential, credential_id,
scopes, mfa }` next to the `AccessContext`, for FB-21. The service-account
mapping is a bridge: `_`-prefixed collection names are reserved, so it cannot
collide with a real collection. **Follow-up for the data core owner:** add a
`Principal::Service` variant and a `scopes` field to `AccessContext`.

Emails are trimmed and lower-cased at signup; lookups use the stored value.

## 3. Token model

| Credential | Format | Lifetime | Stored as |
|---|---|---|---|
| Access token | HS256 JWS, header `kid`; claims `iss=forgebase`, `typ=access`, `st` (user/admin), `col`, `sub`, `sid`, `iat`, `exp`, `jti`, `amr` | 15 min | not stored |
| Refresh token | 32 random bytes, base64url, opaque | session lifetime | HMAC-SHA256 under the pepper |
| Session cookie | 32 random bytes in `fb_session` | session lifetime, idle timeout | HMAC under the pepper (`cookie_hash`) |
| API key / PAT | `fbk_<id16>_<secret>` / `fbp_<id16>_<secret>` (secret 32 bytes) | optional expiry (1–3650 days) | HMAC of the secret; full key returned once |
| One-time link (verify, reset, magic link), MFA challenge | 32 random bytes | 24 h / 30 min / 15 min / 5 min | HMAC |
| Email OTP | 6 random digits | 10 min, 5 wrong guesses then burnt | HMAC of `subject_id:code` |
| Recovery codes | 10 × 10 chars `[a-z0-9]` | until used | HMAC |

- **Access tokens are verified statelessly *and* against their session**: one
  primary-key read checks that the session (`sid`) is not revoked or expired,
  so revocation is immediate, not "within 15 minutes". Only `alg=HS256` with a
  known `kid` is accepted (no `none`, no algorithm confusion); signature
  comparison is constant-time (`hmac::verify_slice`).
- **Refresh tokens rotate on every use.** Each session is one token family:
  using a token marks it used (`UPDATE … WHERE used_at IS NULL`, so two
  concurrent refreshes cannot both win) and issues the next generation. Any
  second use of a used token is treated as theft: the session is revoked
  (`revoked_reason = refresh_token_reuse`), which kills the newest refresh token
  and every access token of the session, and the event is audited.
- **Revocation**: logout (current session), the device list (any own session;
  administrators any session), password change (all other sessions), password
  reset and admin password reset (all sessions), deleting the account (checked
  on refresh, cookie use and API-key use), API key / PAT revoke, service-account
  delete (deletes its keys).

## 4. Sessions and devices

One row in `_forgebase_auth_sessions` per sign-in on a device: method
(`password`, `magic_link`, `email_otp`), MFA flag, IP, user agent, optional
`device_name`, created / last seen / absolute expiry (30 days) and an idle
timeout (7 days, measured by refresh or cookie activity). `GET
/api/auth/sessions` is the device list (`current` marks the caller);
`DELETE /api/auth/sessions/{id}` revokes. Login history is read from the audit
log (`GET /api/auth/login-history`). OAuth/OIDC and passkeys (FB-22) create
sessions through `AuthService::issue_session` after their own verification.

## 5. Key management and rotation

- **Master key**: 32 random bytes in `<data_dir>/auth/master.key`, created
  0600 on first start (data dir is 0700). Two keys are derived from it with
  HMAC-SHA256 and domain labels: the **pepper** (token/code hashing) and the
  **encryption key** (XChaCha20-Poly1305, random 24-byte nonces).
- **Signing keys** (`_forgebase_auth_keys`): random 32-byte HS256 secrets,
  stored encrypted with the key id as associated data; exactly one `active`
  (unique partial index). The active key is rotated after 30 days (checked when
  signing) or on demand (`POST /api/auth/keys/rotate`, administrators). The old
  key becomes `retired` and keeps verifying for the access-token lifetime + 60 s,
  then is deleted. A verifier that meets an unknown `kid` reloads keys once, so
  rotation by another process (CLI) is picked up.
- **Backups**: the database alone cannot decrypt signing keys or TOTP seeds,
  by design. Back up `auth/master.key` separately (FB-83 backups must include it); losing
  it signs everyone out and disables TOTP (users fall back to recovery codes
  and password reset). A wrong master key makes startup fail loudly instead of
  silently issuing new keys.

## 6. Secret storage

Never plaintext:

| Secret | At rest |
|---|---|
| Passwords (users, admins) | Argon2id PHC string, m = 19 MiB, t = 2, p = 1 (OWASP); 16-byte random salt; parameters travel with the hash and old hashes are upgraded at the next login |
| Tokens, codes, API-key secrets, cookies | HMAC-SHA256 under the pepper (a database leak alone cannot even brute-force 6-digit codes) |
| Signing keys, TOTP seeds | XChaCha20-Poly1305 under the derived encryption key, bound to their row by associated data |

Secrets are returned exactly once (tokens at sign-in, API keys and PATs at
creation, recovery codes at enrolment) and never logged: request spans log the
path only, the auth crate logs no credential, and the audit `detail` is built
from non-secret fields and additionally scrubbed of keys such as `password`,
`token`, `code`, `secret`. Tested by capturing all logs at TRACE and scanning
every text and blob cell of the database for every secret used in the test.

Argon2 work runs on blocking threads (`spawn_blocking`). The data core hashes
`password` fields inside its write transaction (synchronous `SecretHasher`);
auth flows pre-compute the hash outside the transaction and hand it over
through a short-lived cache keyed by a keyed digest of the password, so the
single writer is not held for Argon2. Records written by other API paths are
still hashed inside the transaction (**follow-up for the data core owner**:
make `SecretHasher` async or hash before `BEGIN`).

## 7. MFA

TOTP (RFC 6238: SHA-1, 6 digits, 30 s, ±1 step) for users and administrators:
`setup` returns the base32 secret and `otpauth://` URL; `confirm` with a first
code enables it and returns 10 single-use recovery codes. When enabled, every
first factor (password, magic link, email OTP) returns
`{"mfa_required": true, "mfa_token": …}` instead of tokens; `POST
/api/auth/mfa/verify` with a TOTP or recovery code finishes the sign-in
(session `mfa = 1`, `amr` includes `totp`). The last accepted step is stored,
so a code cannot be replayed. Disabling needs a valid second factor.

## 8. Abuse protection

- **Per-IP rate limits** (in memory, fixed windows): 30 credential attempts
  per minute (login, OTP and MFA verify, refresh, link confirmation) and 20
  mail-sending requests per hour (signup, verification, reset, magic link,
  OTP). Exceeding them answers `429 too_many_requests` with `Retry-After`.
  The client IP is the socket address; `X-Forwarded-For` only when
  `trust_forwarded_for` is set (behind your own proxy).
- **Per-account lockout** (persisted in `_forgebase_auth_lockouts`, survives
  restarts): 5 consecutive failures within 15 minutes lock the identifier for
  15 minutes, doubling with each further lock up to 24 hours. Separate counters
  for password login (`pw:`), email OTP (`otp:`), MFA (`mfa:`) and password
  change. Unknown accounts are locked the same way, so lockout does not reveal
  existence. While locked, even the right password gets `429`. A successful
  sign-in clears the counter; a password reset (mailbox control) clears the
  password lockout. Trade-off: an attacker can keep a victim's *password*
  login locked; magic link, OTP and reset still work.
- **Amended by FB-80 (shared addresses, FB-81 finding).** Password sign-ins
  give their attempt back on success, so the per-IP budget counts failures
  (every request is still counted before the password check, so parallel
  guesses stay bounded). Admin sign-in has its own per-IP budget
  (`admin_attempt`), so end-user traffic from the same NAT or proxy cannot
  spend it. A successful admin sign-in sets the `fb_admin_device` cookie
  (`HttpOnly`, `SameSite=Strict`, path `/api/auth/admins/login`, 90 days;
  `<issued>.<HMAC(pepper, issued, email)>`). A browser presenting a valid one
  for the email skips the per-IP budget and the account lockout, with its own
  budget of 5 failures per lockout window; its failures still count towards
  the lockout of other browsers. With `trust_forwarded_for`, the client is the
  last `X-Forwarded-For` entry.
- **Enumeration**: unknown accounts pay for an Argon2id verification of a
  dummy hash (same timing); credential failures are always
  `invalid_credentials`; verification/reset/magic-link/OTP requests always
  answer `202` with the same body. Signup with a taken email answers `409
  email_taken` (accepted trade-off, rate limited).
- Every comparison of a secret is constant-time (`subtle`, `hmac`); every
  random value comes from the OS CSPRNG (`getrandom`), with rejection sampling
  for digits and ids.

## 9. Cookie mode and CSRF

Browser apps may sign in with `"cookie": true`: no tokens in the body; the
response sets `fb_session` (`HttpOnly; SameSite=Lax; Path=/; Secure` unless
`cookie_secure` is turned off for plain-HTTP development) and `fb_csrf`
(readable) and returns `csrf_token`. For cookie-authenticated requests,
`POST/PUT/PATCH/DELETE` must send `X-CSRF-Token`, which must equal
HMAC(pepper, session id) (constant-time), so a token cannot be planted by
cookie tossing. Bearer and API-key requests need no CSRF token (browsers do not
attach them automatically). A stale or revoked session cookie is ignored
(anonymous) and cleared, so a browser can always sign in again. CORS allows the
`X-API-Key` and `X-CSRF-Token` headers; credentials over CORS stay off (cookie
mode is for same-site apps).

## 10. Scopes (API keys and PATs)

`*` | `<area>:*` | `<area>:read|write` | `<area>:read|write:<name>`; `write`
does not imply `read`. The auth layer derives the needed scope from the request
alone, before any handler: `/api/auth/*` → `auth`, `/api/system/*` → `system`,
`/api/v1/<seg>/<name>/…` → `<seg>` with resource `<name>` (e.g.
`collections:read:posts`); `GET/HEAD/OPTIONS` need `read`, everything else
`write`. Missing scope → `403` (`insufficient_scope`). Scopes only narrow: the
owner's principal still goes through the authorizer. A scoped credential cannot
mint a broader PAT. FB-21 can add action-level scopes once `AccessContext`
carries them.

## 11. Audit

`_forgebase_auth_audit` (append-only): time, event (`signup`, `login`,
`login.admin`, `login.mfa_challenge`, `mfa.verify`, `refresh`,
`refresh.reuse_detected`, `logout`, `session.revoked`, `password_changed`,
`password_reset`, `verify_email.*`, `magic_link.requested`,
`email_otp.requested`, `mfa.setup|enable|disable|recovery_codes`,
`admin.created`, `admin.password_reset`, `service_account.created|deleted`,
`api_key.created|revoked`, `pat.created|revoked`, `signing_key.rotated`),
outcome, actor, subject, IP, user agent, request id and non-secret detail.
Changes and their audit row commit in the same transaction. Administrators read
it at `GET /api/auth/audit?event=&subject_id=&before=&limit=`.

## 12. HTTP surface (`/api/auth`)

`signup`, `login`, `refresh`, `logout`, `me`, `verify-email/{request,confirm}`,
`password-reset/{request,confirm}`, `magic-link/{request,confirm}`,
`otp/{request,verify}`, `mfa/verify`, `mfa/totp/{setup,confirm,disable}`,
`mfa/recovery-codes`, `password/change`, `sessions` (+ `DELETE
sessions/{id}`), `login-history`, `tokens` (PATs; + `DELETE tokens/{id}`),
`admins/login`, `admins` (admin), `service-accounts` (+ `/{id}`, `/{id}/keys`),
`api-keys/{id}` (DELETE), `audit`, `keys/rotate`. Bodies are JSON; user flows
take an optional `collection` (default `users`). Mail links point to
`<public_url>/auth/{verify-email|reset-password|magic-link}?token=…`: a client
page POSTs the token to the matching `confirm` endpoint (links are never
consumed by GET, so mail scanners cannot burn or use them).

Mail goes through the `Mailer` trait. The default `DevMailer` writes each
message as JSON to `<data_dir>/mail/` (0700/0600); a production mailer (SMTP or
provider) is a later card.

The OpenAPI document declares the `bearer`, `api_key` (`X-API-Key`) and
`session_cookie` schemes on every `/api/v1` operation (any one, or none:
anonymous callers are allowed through and the authorizer decides).

## 13. CLI

`forgebase admin create --email E --password-stdin` (bootstrap the first
superuser), `forgebase admin reset-password --email E --password-stdin`
(recovery; ends that admin's sessions), `forgebase admin list [--json]`. They
work while the server runs (SQLite serialises the writes) and require a
migrated database. Administrator passwords need at least 10 characters.

## 14. Storage

Migration `0003_auth.sql`: `_forgebase_admins`, `_forgebase_auth_keys`,
`_forgebase_auth_sessions`, `_forgebase_auth_refresh_tokens`,
`_forgebase_auth_one_time`, `_forgebase_auth_mfa`,
`_forgebase_auth_recovery_codes`, `_forgebase_service_accounts`,
`_forgebase_auth_api_keys`, `_forgebase_auth_lockouts`,
`_forgebase_auth_audit`. Times are INTEGER Unix seconds (plain comparisons for
expiry). Forward-only with the pre-migration snapshot of ADR-0001 §4.

## Consequences

- One indexed read per bearer request buys immediate revocation; a cache is
  possible later (FB-81 measures it).
- Per-IP limits reset on restart and are per process; a multi-node deployment
  needs a shared limiter (Redis, Phase 4).
- Configuration uses production defaults from `AuthConfig::for_data_dir`
  (`public_url` from the bind address). **Follow-up**: an `[auth]` section in
  `forgebase.toml` (TTLs, lockout, rate limits, `public_url`, `cookie_secure`,
  `trust_forwarded_for`) needs `forgebase-core` config changes.
- `/api/auth/*` operations are not yet in the OpenAPI document (only the
  security schemes are); follow-up with `utoipa` annotations in `forgebase-auth`.
