# ADR-0013: RESP listener and the Redis/Valkey adapter

- Status: accepted
- Date: 2026-11-09
- Work package: FB-32 (MDF-26). No migration.
- Scope: an optional Redis-protocol (RESP2/RESP3) listener in front of the built-in KV engine (ADR-0005), its authentication and authorisation, pub/sub over RESP, limits, the compatibility matrix, and an optional external Redis/Valkey backend.
- Builds on: ADR-0004 (API keys, PATs, scopes), ADR-0005 (`KvService::exec`, `Reply`), ADR-0003 (`AccessContext`, `Authorizer`).

## Decisions

1. **A new crate, `forgebase-resp`**, not a module of `forgebase-kv`. The engine stays protocol-neutral (no sockets, no auth service); the listener owns TCP, the wire format, connection state and the Redis-specific error codes. `forgebase-server` mounts it (`[resp] enabled = true`).
2. **Off by default.** Config `[resp]` in `forgebase.toml`, env `FORGEBASE_RESP_*`, flags `--resp`, `--resp-host`, `--resp-port`. Default bind `127.0.0.1:6380`. A non-loopback bind logs a warning: **RESP has no TLS** here, so tokens and data cross the network in clear text. Put it behind a tunnel or TLS-terminating proxy (stunnel, haproxy); native TLS is a follow-up.
3. **Protocols.** RESP2 by default; `HELLO 3` switches to RESP3 (null `_`, map `%` for `HELLO`/`HGETALL`, set `~` for `SMEMBERS`/`SUNION`/`SINTER`/`SDIFF`, push `>` for pub/sub). Requests are arrays of bulk strings or inline commands (telnet style, with quotes and escapes). The decoder is incremental and parses each byte once.
4. **Authentication: always required.** An unauthenticated connection may only `PING`, `HELLO`, `AUTH`, `QUIT`; everything else, including unknown commands, answers `-NOAUTH` (the command set is not revealed). `AUTH <token>` and `AUTH <user> <token>` accept **only** a ForgeBase API key (`fbk_...`) or personal access token (`fbp_...`) (`KeyAuthenticator` over `AuthService::authenticate_key`); a password or session token is never accepted over this plaintext protocol. The user name must be `default`, empty, or the credential owner's id; anything else is `-WRONGPASS`. `HELLO 3 AUTH <user> <token>` works. Before `AUTH` a command may have at most 16 arguments of 4 KiB each, and the connection is closed after `auth_timeout` (10 s).
5. **Brute force.** Each failed `AUTH` pauses 100 ms; 5 failures close the connection; 20 failures per client address per minute refuse that address (even with a right token) until the window passes.
6. **Authorisation = the REST rules.** Every data command runs through `KvService::exec`, which asks the same `Authorizer` actions (`KvRead`, `KvWrite`, `KvAdmin`) as `/api/v1/kv`. In addition the key's scopes apply exactly as for HTTP (`kv:read`, `kv:write`, optionally `:<namespace>`; `kv:*`; `*`), checked per namespace; a refusal is `-NOPERM ... lacks the scope kv:write:<ns>`. The fail-closed default authorizer therefore allows administrators and administrator service accounts only.
7. **Re-validation.** The credential is checked again every 30 s (on the next command, and by a timer on subscribed connections), so a revoked or expired key stops working on open connections: `-NOAUTH credential is no longer valid`, then close.
8. **`SELECT` maps to a namespace** of the caller's tenant: `0` is `default`, `1..255` is `db1..db255`, any other valid namespace name (1-64 chars, ADR-0005) is used as given, so `SELECT cache` works in `redis-cli`. Client libraries that put `/N` in the URL get `dbN`. The tenant comes from the credential's `AccessContext`; two tenants never share a key or channel (ADR-0005 scope rule).
9. **Pub/sub** rides the engine's hub. `SUBSCRIBE` subscribes to `(tenant, namespace, channel)` as of the namespace selected at that moment; `PSUBSCRIBE` uses a per-namespace tap and matches the glob on the receiving side (one `pmessage` per matching pattern, like Redis). RESP2: a subscribed connection may only (P)SUBSCRIBE/(P)UNSUBSCRIBE/PING/QUIT/RESET. RESP3: any command, messages arrive as pushes. Delivery is at-most-once (engine rule); a slow subscriber loses the oldest messages (counted in `forgebase_resp_pubsub_dropped_total`). `PUBLISH` replies the number of exact-channel subscribers only; pattern subscribers are not counted. At most 1024 channels plus patterns per connection.
10. **Pipelining.** All complete commands in the read buffer are executed in order and their replies written in one batch (flushed at 1 MiB); a client that stops reading stops being read (back-pressure), and a write that makes no progress for 30 s closes the connection.
11. **Limits** (all enforced while decoding, before any allocation of the payload): `max_connections` 1024 (extra clients get `-ERR max number of clients reached`), `max_bulk_bytes` 16 MiB (a larger argument is a protocol error and closes the connection; the engine's own `max_value_bytes` still answers a normal error), 1 048 576 arguments and 4x `max_bulk_bytes` per command, inline lines 64 KiB, idle timeout 300 s (subscribed connections exempt, like Redis).
12. **Graceful shutdown.** `RunningServer::shutdown` stops accepting, lets each connection finish the command it is executing, closes connections, and after `shutdown_timeout_secs` aborts stragglers (a half-sent command cannot stall it); the KV snapshot flush runs after the listener is down.
13. **Observability.** Metrics `forgebase_resp_connections` (gauge), `forgebase_resp_commands_total`, `forgebase_resp_auth_failures_total`, `forgebase_resp_connections_refused_total`, `forgebase_resp_pubsub_dropped_total`; debug logs per connection.
14. **Backend trait and the Redis/Valkey adapter.** `KvBackend` (`exec`, `subscribe`, `subscribe_all`) is the seam between wire and store. `LocalKv` is the built-in engine. With the cargo feature **`external-redis`** (off by default; nothing needs a Redis to build or test) `external::ExternalRedis` forwards the same commands to a Redis or Valkey server (`redis` crate, `ConnectionManager`): it authorises with the same `Authorizer` actions, forwards **only commands the engine supports** (no `EVAL`, `CONFIG`, `DEBUG`), and confines each caller by prefixing every key and channel with `fb:<len>:<tenant>:<len>:<namespace>:` (length-prefixed so two `(tenant, namespace)` pairs can never share a prefix; glob characters in the prefix are escaped for `KEYS`/`SCAN`, whose results are stripped again). Differences: `DBSIZE` and `FLUSHDB` are refused, pub/sub subscribing is unavailable (`PUBLISH` works), the engine's memory limit, eviction and SQLite snapshot do not apply (the server's own settings do). It is a library seam today; selecting it from `forgebase.toml` for the REST API is a follow-up because the REST handlers still call `KvService` directly.

## Compatibility matrix

Legend: **S** supported, **P** partial (restriction stated), **U** refused with the error shown. The lists live in `crates/forgebase-resp/src/compat.rs`; `tests/protocol.rs` sends every refused command and asserts the exact error text, and `tests/conformance.rs` drives every supported command through redis-rs.

### Connection and server commands (answered by the listener)

| Command | | Notes |
|---|---|---|
| `AUTH`, `HELLO` | S | see decision 4; `HELLO` replies a map (`server`=`forgebase`, `version`, `proto`, `id`, `mode`, `role`, `modules`); `HELLO 4` is `-NOPROTO` |
| `PING`, `ECHO`, `QUIT`, `RESET`, `TIME` | S | `RESET` also drops the auth and the namespace; `PING` while subscribed (RESP2) replies `["pong", msg]` |
| `SELECT` | P | maps to a namespace (decision 8); `SELECT 256` is `-ERR DB index is out of range` |
| `CLIENT ID`, `SETNAME`, `GETNAME`, `SETINFO`, `INFO` | S | the rest (`LIST`, `KILL`, `TRACKING`, ...) is `-ERR CLIENT <sub> is not supported` |
| `COMMAND`, `COMMAND DOCS`/`INFO` | P | empty reply; `COMMAND COUNT`, `COMMAND LIST` list the supported names |
| `INFO` | P | one text block: `redis_version:7.0.0` (the protocol level clients feature-detect on, not a claim of being Redis 7), `forgebase_version`, `connected_clients`, keyspace of the selected namespace |
| `CONFIG GET <pattern>` | P | empty reply; `CONFIG SET` and others are `-ERR CONFIG <sub> is not supported` |
| `SUBSCRIBE`, `UNSUBSCRIBE`, `PSUBSCRIBE`, `PUNSUBSCRIBE` | S | decision 9 |

### Data commands (forwarded to `KvService::exec`)

|---|---|---|
| Keys | `DEL UNLINK EXISTS TYPE EXPIRE PEXPIRE EXPIREAT PEXPIREAT PERSIST TTL PTTL KEYS SCAN DBSIZE` | S. `KEYS` refuses more than `keys_limit` (10 000) matches with an error: use `SCAN`. `EXPIRE` has no `NX/XX/GT/LT` options |
| | `FLUSHDB [ASYNC\|SYNC]` | P: clears the selected namespace of the caller's tenant only; replies `+OK` |
| Strings | `GET SET SETNX SETEX PSETEX GETDEL APPEND STRLEN MGET MSET INCR DECR INCRBY DECRBY INCRBYFLOAT` | S. `SET` takes `NX XX GET EX PX EXAT PXAT KEEPTTL` |

### Errors the engine raises, as clients see them

`WRONGTYPE Operation against a key holding the wrong kind of value`; `ERR value is not an integer or out of range`; `ERR value is not a valid float`; `ERR wrong number of arguments for '<cmd>' command`; `OOM command not allowed when used memory > 'maxmemory'.` (policy `noeviction`); `NOPERM ...` (authorizer or scope denied); `NOAUTH Authentication required.`; `WRONGPASS invalid username-password pair or user is disabled.`; `ERR Protocol error: ...` (then the connection closes); storage failures are logged and answer `ERR internal storage error` without details.

## Changes outside the new crate

- `forgebase-kv` (additive, **no bug found or fixed**): `KvService::subscribe_all` (a per-scope tap in the pub/sub hub, needed because the hub had no way to receive "every channel of a namespace", which `PSUBSCRIBE` requires) and `pub use glob_matches`. Two unit tests in `pubsub.rs`. Noted, not changed: engine `FLUSHDB` returns the number of removed keys where Redis returns `OK`; the listener maps it.
- `forgebase-core`: `[resp]` config section (`RespConfig`: `enabled`, `host`, `port`, `max_connections`, `max_bulk_bytes`, `idle_timeout_secs`), env overrides, validation; `forgebase.example.toml` and the `init` template document it.
- `forgebase-server`: starts and stops the listener, `RunningServer::resp_addr()`, a bind failure is `ServerError::Bind` with `(resp)` in the address and releases the data directory.
- `forgebase-cli`: `--resp`, `--resp-host`, `--resp-port`; `serve` prints the Redis URL.

## Testing

`cargo test -p forgebase-resp` (59 tests): wire codec unit tests (split at every byte, limits, inline quoting); a conformance suite that drives **every supported command** and every refused command through redis-rs / a raw socket; pipelining (2 000 mixed commands, 10 000 `PING`s in one write); auth gate, wrong users and tokens, brute-force limits, pre-auth limits and deadline; Authorizer and scope enforcement; `SELECT` namespaces; cross-tenant isolation of keys, `FLUSHDB`, channels and patterns; RESP2 and RESP3 pub/sub; a subscriber that stops reading; max bulk, connection and idle limits; graceful shutdown with half-sent commands; the production authenticator against the real auth service (API key, PAT, revoked key on a live connection). `crates/forgebase-server/tests/resp.rs` covers the listener through the server lifecycle (off by default, API key from the real auth service, data surviving a restart, bind error), and `tests/integration/cli_e2e.rs` the `--resp` flags. The external adapter's key rewriting and reply conversion are unit-tested without a server; one `#[ignore]` test runs against a real Redis when `FORGEBASE_TEST_REDIS_URL` is set. `redis-cli` is not installed on the build machine; its wire format (arrays of bulk strings, inline) is covered by the raw-socket tests.

## Limitations and follow-ups

- No TLS (decision 2). No `CLIENT TRACKING` or client-side caching. No `MULTI`. RESP3 uses map/set only where listed; scored ranges are flat.
- The tenant of a connection is whatever the credential's `AccessContext` says; real tenant selection arrives with FB-21's policy engine and the credential-to-tenant mapping.
- `SUBSCRIBE` is bound to the namespace selected when it was issued.
- The external backend is not yet selectable from `forgebase.toml` (decision 14), and the REST KV API does not use it.
- Memory use of an authenticated connection is bounded by `max_request_bytes` (64 MiB by default) per command plus pending replies; very large pipelined replies are flushed at 1 MiB steps.
