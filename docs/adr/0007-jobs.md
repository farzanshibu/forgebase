# ADR-0007: Durable jobs

- Status: accepted
- Date: 2026-11-07
- Work package: FB-61 (MDF-34)
- Scope: job queue, schedules, workers, leases, HTTP API, authorisation hook.
- Builds on: ADR-0001 (one writer, error model), ADR-0003 (`AccessContext`, `Authorizer`).

## Decisions

1. **A job is a row** (migration `0007_jobs.sql`: `_forgebase_jobs`, `_forgebase_job_events`,
   `_forgebase_job_schedules`, `_forgebase_job_workers`). Every state change is one committed
   transaction on the single writer, so claims and completions are atomic and survive restarts.
   Times are Unix epoch milliseconds (API: RFC 3339).
2. **States**: `queued` (incl. delayed and waiting to retry), `running`, `succeeded`, `dead`
   (dead-letter queue), `cancelled`. `retry` moves `dead`/`cancelled` back to `queued`.
3. **Leases.** `claim` sets `lease_id` (random fencing token) and `visibility_until = now +
   visibility_timeout_ms`. `heartbeat` extends it. `complete`/`fail`/`heartbeat` must present the
   current lease; otherwise `409 lease_lost`. Expired leases are re-queued (or dead-lettered when
   attempts are used up, or cancelled if cancellation was requested) by every claim and by the
   pool's maintenance tick. A lost lease counts as an attempt; a graceful `release` does not.
   This gives at-least-once execution with exactly-once *completion*; handlers should be idempotent.
4. **Retries.** `delay = min(max, base * 2^(attempt-1))`, reduced by random 0-25% (jitter), default
   base 1 s, max 1 h, 5 attempts. Non-retryable failures go straight to the DLQ.
5. **Idempotency**: unique `(queue, idempotency_key)`; a repeat enqueue returns the first job (`200`).
6. **Cron**: own small parser (5 fields, or 6 with leading seconds; UTC; no new dependency).
   Firing inserts a job with key `schedule:<id>:<due ms>` and advances `next_run_at` in one
   transaction, so it happens once even with racing processes. Firings missed while down collapse
   into one.
7. **Cancellation**: queued jobs are cancelled at once; running jobs get `cancel_requested`, which
   the worker sees in the heartbeat response (the in-process pool exposes `JobContext::cancelled()`).
8. **Handlers**: Rust trait `JobHandler` + `JobRegistry` by `kind`. The in-process pool claims only
   registered kinds, so other kinds are left to external workers (HTTP). Wasm functions (FB-60)
   register a handler later.
9. **Pool** (`start_pool`): polls, runs up to `concurrency` jobs, heartbeats every third of the
   visibility timeout, fires schedules, reaps leases, purges succeeded/cancelled jobs after 7 days
   (DLQ never purged). Shutdown stops claiming, waits `shutdown_grace`, then aborts and releases.
10. **Authorisation**: no auth code here. Each service method calls
    `DataService::authorize_action` (new, no collection) with new `Action` variants `ReadJobs`,
    `EnqueueJob`, `ManageJobs`, `WorkJobs`; `Decision::Filter` is treated as deny. The HTTP layer
    authorises before parsing a body. The pool acts as `AccessContext::system()`.
11. **Mounting**: `forgebase-jobs` depends on `forgebase-api` (error envelope, `Access`), so the API
    crate gains `RouterOptions::extensions` (`ApiExtension`: routes + OpenAPI fragment) instead of
    depending on jobs. The server mounts `/api/v1/jobs` through it.

## Known limits / follow-ups

- Queue-level policy (FB-21) cannot see the queue name: authorizer gets `None` as collection.
- No per-queue concurrency limit, no long-poll claim, no pool settings in `forgebase.toml`.
- Scheduler tick is 250 ms; cron precision is about that.
- Dependencies: none new (uuid, time, utoipa, tower-http, axum already in ADR-0002).
