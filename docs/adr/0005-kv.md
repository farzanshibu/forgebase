# ADR-0005: Key-value engine and its persistence

- Status: accepted
- Date: 2026-11-08
- Work package: FB-31 (MDF-25). Migration `0005_kv.sql`.

## Decision

Memory is authoritative; SQLite is a write-behind snapshot.

- All keys live in an in-memory ordered map (`forgebase-kv`). Reads and writes never touch SQLite.
- Keys changed since the last flush are written to `_forgebase_kv_entries` in one transaction every `flush_interval` (1 s) and at shutdown. All keys are loaded back at start-up; expired keys are skipped and their rows deleted on the next flush.
- One row per key: `(tenant, namespace, key)` primary key, value as JSON (binary parts base64, sorted-set scores as raw f64 bits), `expires_at` and `updated_at` in unix ms.

Why not SQLite as the primary store: every command would pay a write transaction on the single writer connection, contending with the data core. Why not memory only: SPEC 4.4 wants an embedded deployment that keeps cache state across restarts, and "no Redis needed" should still survive a restart.

## Durability

A crash loses up to `flush_interval` of writes (and nothing flushed earlier). Clean shutdown loses nothing. This is cache-grade durability by design: **KV data must not replace durable SQL records** (SPEC 4.4). A failed flush re-marks the keys dirty and retries.

## Memory limit and eviction

`max_memory_bytes` (default 256 MiB, `0` = unlimited) counts an estimate (payload + 128 B per key + 32 B per member), not RSS. Policies: `allkeys-lru` (default), `volatile-lru` (only keys with TTL), `noeviction` (writes that grow memory fail with `kv_out_of_memory`, 503). The newest key is never evicted, so one oversized value can exceed the budget until the next write. Eviction is exact LRU (ordered tick index), O(log n).

## Expiry

Lazy on access plus a background sweep every second. A key is gone at exactly its deadline.

## Tenant isolation

Every command runs in a scope `(tenant, namespace)` built from `AccessContext.tenant` (`None` = the `default` tenant, others prefixed `t:`). The store API takes only a scope, never a bare key, so a command cannot address another scope. Pub/sub channels are scoped the same way. Namespace names: 1-64 chars, `[A-Za-z0-9]` first, then `[A-Za-z0-9_.:-]`.

## Authorisation

Three new `Action` variants: `KvRead`, `KvWrite`, `KvAdmin` (flush namespace, stats). Each request is authorised before data is touched; a batch asks for every class it contains and runs nothing if any is denied. A `Decision::Filter` answer cannot be applied to KV and is treated as a denial. The default authorizer allows administrators and the system only; anonymous gets 401.

## Command layer

`KvService::exec(ctx, ns, args) -> Reply` takes Redis-style byte arguments and returns a RESP-shaped `Reply` (Nil, Status, Int, Bulk, Array). No HTTP or RESP types leak in, so FB-32 maps RESP onto it directly. `spec(name)` gives arity and access class for a command.

Supported: PING; DEL UNLINK EXISTS TYPE EXPIRE PEXPIRE EXPIREAT PEXPIREAT PERSIST TTL PTTL KEYS SCAN DBSIZE FLUSHDB; GET SET(NX XX GET EX PX EXAT PXAT KEEPTTL) SETNX SETEX PSETEX GETDEL APPEND STRLEN MGET MSET INCR DECR INCRBY DECRBY INCRBYFLOAT; HSET HSETNX HGET HMGET HGETALL HKEYS HVALS HLEN HEXISTS HDEL HINCRBY; LPUSH RPUSH LPOP RPOP LLEN LRANGE LINDEX LSET LREM LTRIM; SADD SREM SISMEMBER SMEMBERS SCARD SPOP SUNION SINTER SDIFF; ZADD(NX XX CH) ZREM ZSCORE ZRANK ZREVRANK ZRANGE ZREVRANGE ZRANGEBYSCORE ZINCRBY ZCARD ZCOUNT ZPOPMIN ZPOPMAX; XADD XLEN XRANGE XREVRANGE XREAD(non-blocking) XDEL XTRIM(MAXLEN); PUBLISH.

Not supported (not a Redis replacement): transactions (MULTI/WATCH), Lua, blocking commands (BLPOP, blocking XREAD), consumer groups, replication, SELECT/databases (namespaces replace them), geo, HyperLogLog, bitmaps, `KEYS` over `keys_limit` (use `SCAN`). `SCAN` cursors are key-ordered and stable under concurrent changes. `ZADD` scores must not be NaN. Sorted-set rank is O(n).

Atomicity: one store lock; each command is atomic and `/batch` runs commands with no other command in between (no rollback).

## Pub/sub

In-process `tokio::sync::broadcast` per `(scope, channel)`. At-most-once, not stored; a slow subscriber gets a `lagged` event. Exposed over REST as SSE (`GET /api/v1/kv/{ns}/subscribe/{channel}`). Limits: `channel_capacity` 256, `max_channels` 10 000.

## Limits

Key 512 B, value 16 MiB (configurable), JSON body 4 MiB, `KEYS` 10 000 results.

## Dependencies

None new: axum, base64, serde, tokio, tower-http, utoipa, futures-util, url are already recorded in ADR-0002. `forgebase-api` gains `router_with` (extra routes plus an OpenAPI fragment merged into `/api/openapi.json`).

## Follow-ups

Config keys in `forgebase.toml` (`[kv]`) once config is extended (the engine runs on `KvConfig::default()` now); metrics export; FB-32 RESP listener; policy-engine rules for `Kv*` actions (FB-21).
